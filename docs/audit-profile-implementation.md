# Audit Log and self-service profile implementation

Implemented locally; no commit, push, deployment or production-data access. The initial working tree was clean. No migrations or historical record rewrites were needed.

## Original limitations

- `/dashboard/audit-log` was a placeholder. Its backend allowed accountants with history permission to query the global route, lacked pagination and most filters, and serialized raw legacy metadata/descriptions.
- Daily Sheet history depended on that global route.
- There was no self-service profile editor or password-change endpoint.
- Users have `full_name`, not separate first/last names or a phone field. Email is the login identity, with no verified-email-change workflow.
- JWT authentication did not check password revocation; the custom login serializer did not update last login.

## Audit browsing and security

Only authenticated Super Admins can list, retrieve or export the global log. Authenticated accountants receive 403, including when manipulating agency, actor or Daily Sheet query parameters. The frontend hides this area from accountants and renders Access Denied for direct navigation. Django enforces the API permission independently.

The table includes date/time, actor display name, current actor role, human-readable action, module/resource, agency, safe numeric record identifier, result, short generated description and a detail button. Events are ordered by descending creation time and ID. Native modal dialogs support Escape, focus containment and return focus to the initiating button.

Backend filters: search, date from/to (inclusive), actor ID, role, agency ID, module/resource type, action code, result, and the retained Daily Sheet filter. Search covers actor name, reference, action and resource type. Filtering is explicitly applied; ordering is fixed newest-first. Pagination defaults to 25 rows, configurable up to 100. The browser never retrieves the entire history.

Details use an allowlist of typed identifiers, permission/status booleans and known changed-field names. Arbitrary nested legacy payloads, personal values, passwords, hashes, tokens, cookies, CSRF data, request bodies, connection strings, secret keys, workbook contents, card/payment secrets and tracebacks are not serialized. Original free-text descriptions are replaced with generated action summaries. Non-numeric references are redacted. Reads do not mutate stored events.

Result is derived from the event action: `_FAILED` is Failed, other recorded events are Success. The schema has no independent outcome or actor-name/role snapshot fields; actor identity reflects the current account, as explained in the screen.

CSV export is generated by Django with the same permission and filters, safe table columns, no metadata, and formula-injection escaping. Requests matching more than 10,000 events are rejected with guidance to narrow filters; iteration is additionally capped at 10,000. Export uses applied filters rather than unsaved filter edits.

The API is read-only: no create, update or delete routes. Model immutability and existing historical data are preserved.

## Audit coverage

Existing events were retained without duplication for accountant creation/update and agency assignment replacement; agency creation/update/activation; Person/Sub-Agent/Terminal creation and reassignment; Daily Sheet creation/import/confirmation/status transitions; payment payer updates; obligation creation/cancellation; payment posting/reversal; game schedules and holiday overrides.

Added safe events for successful login, logout, profile update, password change, and direct assignment create/update/delete operations. Direct assignment mutations and events are transactional. New User audit entries omit personal field values and use safe summaries. Existing stored entries are untouched. Profile/password events contain changed-field names only. No-op profile saves do not create events.

Scoped, paginated Daily Sheet history remains available only within the user's authorised agency and with history permission. It uses the safe serializer and cannot broaden scope through query parameters.

## Profile and password

All authenticated users can read their own display name, login email, role, assigned agencies, account status and last login. Only `full_name` is editable. Email, role, agency assignments, ID and active status are read-only; submitted protected or unknown fields are rejected rather than silently accepted. No speculative schema fields were added.

The UI explains the single-name model and read-only email, preserves values on validation errors, shows field-level feedback, prevents duplicate saves, announces success, and links My Profile from navigation and the header identity area.

Password changes require the current password, a matching confirmation and Django password validation. They are throttled using the existing password-reset throttle scope. All outstanding refresh tokens are blacklisted, and password-based JWT revocation rejects existing access tokens immediately. The UI clears password fields, clears local authentication cookies through the existing logout route, explains that sessions are invalidated, and offers a Sign in again link.

Enabling `CHECK_REVOKE_TOKEN` also means pre-existing tokens without the revocation claim will require sign-in again when this change is eventually released. No release was performed.

## Endpoints and controlled proxy

| Method | Endpoint | Access |
| --- | --- | --- |
| GET | `/api/audit-logs/` | Super Admin |
| GET | `/api/audit-logs/{id}/` | Super Admin |
| GET | `/api/audit-logs/export/` | Super Admin |
| GET | `/api/profile/` | Authenticated self |
| PATCH | `/api/profile/` | Authenticated self, full name only |
| POST | `/api/profile/change-password/` | Authenticated self |
| GET | `/api/daily-sheets/{id}/history/` | Super Admin or scoped history permission |

Frontend proxy paths mirror these under `/api/backend/` with exact method/path allowlists. Only audit export is treated as a binary download. Existing CSRF handling remains in use.
